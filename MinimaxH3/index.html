00一页速览

用一个具体例子走一遍：让模型画「一只戴红帽子的猫在喝咖啡」。下面四张卡就是完整的四步。

第 1 步 让它会画
喂几百万组「图片 + 描述」，它学会猫、帽子、咖啡杯长什么样。这一步叫预训练。此时它画得出来，但好不好看、听不听话，没人保证。
第 2 步 画 8 张，打分
同一个要求，让它画 8 张，得到 8 个不同版本。再用一个专门打分的模型逐张给分：6.2、7.1、5.8、7.4、6.9、6.5、7.8、6.0。平均 6.7，高于平均的 7.1 / 7.4 / 7.8 就是「好」的方向。
这一步就是 GRPO：不看绝对分数，只看「在你这 8 张里排前面还是后面」。
第 3 步 让它更爱画好的
把第 2 步里高分那几张的「出现可能性」往上推。下次同样的要求，更容易画出 7 分以上的。同时要拴住它别跑偏 —— 分数一路涨、画面却越来越丑，是这套方法最常见的翻车方式。
第 4 步 换成视频，多两个麻烦
麻烦一：视频是一笔一笔画几十笔，每一笔都是算死的。模型没法告诉你「它本来有多大把握画出这条路径」，而第 3 步正需要这个数 —— 解法是每一笔都撒一点随机噪声，把「把握」变成能算的数。
麻烦二：几十笔全练太贵，只挑其中一段练。补上这两件事，就是 Flow-GRPO。
第 5 步（H3 这类音视频模型）：算法还是上面四步，难的是工程 —— 声音会不会在某一步悄悄丢了、改过的东西有没有真的生效。目前跑得通的两条路：一条 2 张卡、只改一小部分参数，一条 8 张卡、同时给画面和声音打分。
想去看论文时的名词对照：第 2 步 = GRPO；第 4 步的「每笔撒噪声」= ODE→SDE，「只挑一段练」= Denoising Reduction；两条落地路线 = Flow-GRPO 与 DiffusionNFT。名词就这几个，事情你已经走完了。
PART 1原理：RL 为什么能改扩散模型1–6 节

1RL 到底在优化什么

把模型想象成一个学生，把奖励模型（reward model）想象成阅卷老师。RL 后训练就是：让学生对同一道题写 G 份答案，老师逐份打分，然后告诉学生「哪份比你自己平均水平更好，以后多写这种」。

Policy 策略
就是模型本身。它给每个可能的输出分配一个概率。RL 只改概率，不改结构。
Rollout 采样
用当前模型真正生成一批样本。视频模型里就是跑一遍完整的去噪采样。
Reward 奖励
一个打分函数。可以是规则（数对了几个物体）、也可以是模型（PickScore / HPS / VideoAlign / CLAP）。
Advantage 优势
「这份样本比基线好多少」。正数→提高它的概率，负数→降低。
KL 约束
防止模型为了骗分跑得太远，把自己的语言/画风搞崩。通常对参考模型加一个惩罚项。

先混个脸熟：后面反复出现的 12 个词

不用背，看一遍有个印象就行。遇到不懂的随时回来查这一节。

名词一句人话
价值网络 / critic另训一个模型，专门预测「这道题按当前水平大概能拿几分」，这个预测分就是及格线。PPO 需要它，GRPO 把它删了。
基线 baseline判断「好还是差」的参照物。只知道自己 85 分没用，得知道平均分是 70 还是 90。
log-prob 对数概率模型给某个输出打的「概率分」，取对数只是为了数字好算、不溢出。RL 靠它判断「这次比上次更可能还是更不可能」。
轨迹 trajectory一次完整生成的全过程。视频里就是从纯噪声一路去噪到成片，几十步，每步算一个动作。
去噪步整条轨迹里的一小步，一步只把噪声减掉一点点。扩散模型的「动作」就是这些步。
确定性 ODE一条死路：同一张起始雪花图，画一百次都是同一张。没得挑，也就算不出「把握」。
SDE在上面那条路上，每走一步随机左右晃一下。整体还是走到同一片地方，但每次落的点不一样，于是能挑、也能算出「这次走成这样的把握」。
重要性比率 ρ新版模型想画这个结果的意愿 ÷ 老版本的意愿。大于 1 说明「更想画了」，更新时给它加权。
clip 裁剪把 ρ 限制在 0.8~1.2 之间，一次更新不许改动太猛，防止训练崩掉。
on-policy样本必须由「当前这版模型」现场生成，不能用旧数据凑数，否则比率就失效了。
分叉 branching从同一个中间状态同时往 G 个方向走，前半段共享，省算力。Flow-GRPO 提速的关键。
奖励黑客 reward hacking模型找到骗分的捷径：分数一直涨，人看着却更差。RL 最主要的翻车方式。

和监督学习的关键区别

维度SFT / 监督微调RL 后训练
信号标准答案（token 级）一个分数（序列级，甚至只有一个数）
数据静态数据集，反复用模型自己现场生成，分布随训练变化（on-policy）
优化目标最大化正确 token 的似然最大化期望奖励，同时别偏离太远
典型失败分布外不会做reward hacking：分数涨了，人看着更差
一句话：SFT 教模型「像人一样写」，RL 教模型「往人更喜欢的方向多写一点」。前者学格式，后者学偏好。

为什么生成模型也需要 RL

预训练解决「会不会生成」，SFT/蒸馏解决「听不听得懂指令」，而 RL 解决的是那些很难写成监督标签、但很容易打分的东西：文字渲染是否清晰、人体结构是否合理、视频里物体是否一直存在、口型和声音是否同步、品牌 logo 有没有变形。这些目标写成 loss 很别扭，写成一个 reward model 却非常自然。

2算法谱系：从 PPO 到 Flow-GRPO

这一行字看起来很多，其实只在回答两个问题：基线从哪来、要不要真的采样。看懂这两条线，整棵树就顺了。

  • 2017 PPO：actor 生成、critic 估基线、clip 限制更新幅度。稳，但要养四个模型（策略、价值、奖励、参考）。
  • 2023 DPO：跳过采样和奖励模型，直接拿「好/坏」成对数据做监督式优化。便宜，但只能用离线数据。
  • 2023 DDPO / DPOK：第一次把扩散采样过程当成多步决策，用策略梯度直接优化图像奖励。证明了「扩散模型可以 RL」，但极贵。
  • 2024 GRPO：DeepSeekMath 提出。把 critic 删掉，用同一道题的 G 个样本的均值/标准差当基线。省一个模型，训练稳定。
  • 2025 Flow-GRPO / DanceGRPO：把 GRPO 搬到扩散与整流流上。关键动作是把确定性 ODE 换成等价 SDE，让轨迹可采样、可算概率。
  • 2025 下半年 MixGRPO / BranchGRPO / TempFlow-GRPO / Flash-GRPO：全在抠同一件事——rollout 太贵。混合采样、树状共享前缀、时间步重要性、同时间步分组，各切一刀。
  • 2025 下半年 GRPO-Guard / DiffusionNFT / CPS：前两个解决「训练久了反而变差」，CPS 解决「SDE 噪声加多少」。属于稳定性补丁。
  • 2026 全模态扩展：从图像扩到视频、音视频联合（H3 这类），奖励从单一美学分扩到「文本-视频-音频」多模态一致性。
怎么记：PPO 是「请助教估分」，DPO 是「只看出分后的排名，不再考试」，GRPO 是「不请助教，直接看班里这 8 个人的平均分」。Flow-GRPO 之后的所有工作，都是在这个班上想办法「少考几次、少算几遍」。

3GRPO 到底改了什么

只改了一件事：把「优势」的算法从「减 critic 的预测」换成「减同组平均分」。其他都是 PPO 的老配方。

# 1. 同一道题 q，采样 G 条回答，各打一个分 r r_1, r_2, ..., r_G # 2. 组内标准化，得到优势（这就是「及格线」） A_i = (r_i − mean(r_1..r_G)) / (std(r_1..r_G) + ε) # 3. PPO 式裁剪目标 + KL 约束 ρ_i = π_θ(o_i|q) / π_old(o_i|q) L = −E[ min(ρ_i·A_i, clip(ρ_i, 1−ε, 1+ε)·A_i) ] + β·KL(π_θ ‖ π_ref)

注意三个细节，它们解释了很多后续论文的动机：

细节 1
除以 std 是把双刃剑。奖励尺度被抹平，学习率好调；但如果一组里 8 个样本得分几乎一样（std≈0），优势会被放大成噪声。这就是「组内无方差」问题。
细节 2
G 不能太小。G=2 时均值只有两个点，基线很粗；G 越大越准，但 rollout 成本线性增长。视频场景通常卡在 8~16。
细节 3
不需要 critic，但需要 log-prob。语言模型算 token 概率很容易，扩散模型算整条轨迹概率很难——这正是第 4 节那堵墙。
细节 4
KL 是刹车。β 太小→跑飞、画面崩；β 太大→学不动。实践中常配合「参考模型定期同步」而不是死磕 β。
对比项PPOGRPO
需要的模型策略 + 价值 + 奖励 + 参考（4 个）策略 + 奖励 + 参考（3 个）
基线来源critic 预测的 V(s)同组样本均值
显存高（critic 常与策略同规模）低约 1/3
样本效率每题采 1 条也能学每题必须采一组（G≥4）
主要风险critic 估不准 → 优势失真组内全对/全错 → 优势为 0

4为什么扩散模型不能直接套 GRPO

语言模型是「一个词一个词往外蹦」，扩散模型是「一团噪点反复擦几十遍」。麻烦出在擦的方式上：现在这些模型擦得太「死」—— 每一步都分毫不差。而 RL 需要两样东西：多试几次能试出不同结果，以及知道这次成功的把握有多大。这两种东西它都给不了。

用大白话说，卡在三件事上

卡点 1 没得挑
给它同一张起始雪花图，重来一百次，第 1 步、第 2 步……一直到第 50 步，全都分毫不差，最后是同一张图。RL 的本事是「多试几次、把好的挑出来」，可试 8 次等于只试了 1 次 —— 没有差别，就分不出好坏。
卡点 2 没有「把握」这个数
RL 改参数前要问一句：模型走出这条路径的把握有多大？死路径的答案永远只有两个 —— 100% 或 0%，没有中间值。一个永远等于 100% 的数字，加减之后还是 0，梯度推不动任何参数。
卡点 3 谁该领功说不清
一张图好看，是第 3 步擦对了还是第 40 步？几十步共用一个总分，功劳分不下去。这也是 PPO 要额外请一个「助教估分」（价值网络）的原因。
把术语换成人话：上面说的「死路径」，论文里叫 确定性 ODE；「把握多大」这个数，论文里叫 概率 / log-prob。名字吓人，事情就是你刚才读到的这两句。

还有一堵「钱墙」

语言模型一个 rollout 是几百个 token；视频模型一个 rollout 是几十步 × 每步一次 33B 前向。H3 这种模型，一条 768p、4 秒的样本就要跑满整条去噪链，batch 4 × n=16 就是 64 条。所以 2025 年之后的论文，一大半篇幅都在讲怎么少跑，而不是怎么把公式写得更漂亮。

先记住这个判断：扩散 RL 的瓶颈是采样成本与概率可算性，不是「奖励设计得多花哨」。看到一篇新论文，先问它动了这两件事里的哪一件。

5Flow-GRPO 的两把钥匙

第一把钥匙把「没随机性」变成「有随机性」，第二把钥匙把「太贵」变成「还能接受」。

钥匙一：每擦一步，随机抖一下

如果只想记一句话：原来的擦法是死路径，每步随机抖一下，就有了岔路。论文把这个「抖过之后」的版本叫 SDE，把原来那个叫 ODE —— 名字先不用管，事情就是这么件小事。

抖多大也有讲究。抖动是对称的、平均为零：有人往左偏 5 厘米，就有人往右偏 5 厘米，平均下来还在原地。所以整体该出什么图没变，只是每条具体路径变得独一无二。好比一条走廊，让 1000 个人从这头走到那头，每人每步随机左右晃几厘米 —— 走完人群还是沿走廊前进，但每个人脚印都不一样，于是才有「哪种走法更好」可评。

有得挑了
同一句 prompt、同一张起始噪点，也能采出 G 个不同结果，组内比较才有意义。
有「把握」可谈了
每一步的抖动都是随机的，所以「这次抖成这样」的把握能一步步乘出来（取对数就是相加），RL 才有东西可调。
抖动幅度可调
抖多大是一个旋钮：调到 0 就退回原来的死路径，抖太猛画面会糊。实践里常用 0.7~0.9 这一档。
# 确定性 ODE（原始采样器）：死路径，每步只按模型算的方向走 x_{t−1} = x_t − v_θ(x_t, t)·Δt # 等价 SDE：只多了最后一项，就是每步撒的那一撮随机雪花 x_{t−1} = x_t − v_θ(x_t, t)·Δt + σ_t·√Δt·ε, ε ~ N(0, I) # 两式只差末尾的 + σ_t·√Δt·ε；σ=0 时一个字都不差，完全退回 ODE

钥匙二：减少「要训练的去噪步」

一条轨迹 50 步，没必要 50 步都参与更新。Flow-GRPO 的做法是随机抽一段步数（Denoising Reduction）来训练，其余步照常采样但不回传梯度。再进一步是 Flow-GRPO-Fast：只在单个时间步上让 G 条轨迹分叉，后半段共享确定性轨迹——一次前向变成 G 次前向的只有一步，成本骤降。

一个容易忽略的参数：CPS（Coefficients-Preserving Sampling）指出，噪声强度不能随便取。它需要与采样器的系数保持匹配，论文里给的经验值在 noise_level ≈ 0.8 附近。取错了不会报错，只会让「奖励涨、画面糊」同时发生。
顺序别搞反：先确认 SDE 版本能正常出图（关掉 RL，只改采样器，肉眼对比）。这一步不过关，后面所有训练曲线都不可信。

62025-2026 的改进树

这些工作几乎都在回答同一个问题：怎么在有限算力下，让组内比较既便宜又有信号。按「它动了哪一刀」来记最省力。

方法动的那一刀一句话理解
DanceGRPO统一表述把扩散和整流流都写成 SDE，图像/视频/I2V 共用一套实现。工程上最值得先读的代码库。
MixGRPO采样路径前段用 ODE 省算力，后段用 SDE 做探索，再加滑动窗口只训窗口内的步。
BranchGRPO轨迹共享树状分叉：多条轨迹共享前缀，只在关键节点分开，rollout 去重后成本大降。
TempFlow-GRPO信用分配按时间步重要性加权，并给分叉过程加中间奖励，缓解「几十步共享一个分」。
Flash-GRPO分组方式在同一个时间步内分组比较，再做时间梯度校正，报告约 6× 加速。
GRPO-Guard数值稳定性发现重要性比率系统性偏小，导致 clip 形同虚设、模型过优化。用 RatioNorm + 梯度重加权修。
DiffusionNFT换范式不做轨迹 log-prob，改用「前向加噪 + 正负样本对比」，因此可以直接套黑盒采样器。
CPS噪声强度给 SDE 的噪声系数定规矩，避免「分涨了图糊了」。

三条实用结论

结论 1
先降成本，再谈效果。Branch/Mix/Flash 这类工作的收益是「同样的卡能多跑几轮」，对个人复现比刷点更重要。
结论 2
训练后期变差是普遍现象。GRPO-Guard 指出的 clip 失效不是个例，长训练务必监控「代理分 vs 金标分」两条曲线。
结论 3
算不出 log-prob 时，DiffusionNFT 是逃生通道。它绕开概率计算，代价是失去部分理论保证。
结论 4
别一次改三个地方。换采样器、换奖励、换分组方式分开验证，否则出错时无法定位。

8奖励怎么设计（比算法更重要）

同一套 GRPO 代码，换个奖励函数就是另一篇论文的效果。奖励选错，算法再好也只会更快地跑偏。

类型代表管什么坑
人类偏好分PickScore / HPSv2 / HPSv3整体美观、像不像人喜欢的图容易被「高饱和、强对比」骗分
图文一致性ImageReward / UnifiedRewardprompt 里的物体、数量、属性细粒度计数仍然弱
规则校验GenEval / OCR / 检测器可验证的硬指标（文字、个数）规则太窄，模型会只优化那一点
视频质量VideoAlign / VideoScore / VisionReward时序一致性、运动合理性打分慢，常成为瓶颈
音频-文本CLAP声音和描述是否匹配对音质细节不敏感
音频-视频ImageBind口型/动作与声音是否同步跨模态对齐偏粗

三条原则

1
奖励要「难骗」。先用小学习率跑 200 步，看分数涨的同时人眼是否也觉得变好。这条不过，别加步数。
2
至少两个奖励，且量纲要对齐。加权求和前先各自归一化，否则某一项会独占梯度。H3 的路线 B 就是 CLAP + ImageBind 两项。
3
留一个「金标」不做训练目标。比如人工抽检 50 条，只用来监控。代理分涨、金标分跌，就是奖励黑客的明确信号。
最常见的翻车：奖励模型本身有偏（比如偏爱某种画风），RL 会把这个偏好放大到极端。表现是「分数创新高，画面全是一个味道」。

9落到 MiniMax H3：一条能跑的路

先认清这个模型的形状，再决定 RL 挂在哪。H3 不是一个普通 DiT，它是「文本-视频-音频」打包成一条序列的联合模型，这决定了你做 RL 时必须小心拆包。

模型事实（做 RL 前必须知道的）

主干
33B dense 单流 DiT，其中约 13B 在 AdaLN 分支；参数量大，全参训练不现实，LoRA 是默认选择。
文本编码
Qwen3-VL-32B 第 50 层输出，不是 CLIP/T5，提特征的方式要和官方推理脚本保持一致。
视频 VAE
VisualVAE f16t4d24，24 通道，patchify 1×2×2。潜在张量的形状算错一步，整条链路全错。
音频 VAE
AudioVAE 把 32kHz 压到约 40Hz，左右声道独立编码。
输出规格
24 FPS、4~15 秒、768p；2K 是用 in-context 再生成，不是直接一次出。
采样
CFG 已蒸馏，推理时 guidance scale 固定 1.0，不要沿用 SD 那套 3.5~7 的习惯。
时间步
用 data fraction（0~1 连续值），不是整数步号。写 SDE 时别把 t 当成 1..50。
速度方向
velocity 的符号与 diffusers 里的约定相反，直接搬公式会训成「反向去噪」。
序列组织
音视频 token 打包成一条 packed 序列，靠 3D MM-RoPE 区分模态与时空位置。

CFG、AdaLN、adapter 头：SFT 到底在改哪里

这三个词经常一起出现，说的其实是三件不同的事。

CFG
让画面更听提示词的放大手段。每一步算两遍：一遍带完整提示词，一遍带空提示词，然后 结果 = 空提示的结果 + s × (带提示的结果 − 空提示的结果)。s 越大越听话、也越容易过曝，s=1 等于不加力。代价是每步前向两遍。
CFG 蒸馏
把「算两遍才有的效果」直接训进一遍里。H3 已经蒸馏过，所以推理固定 guidance=1.0。再手动填 5、7，等于在已经加过力的模型上再叠一层，结果是过曝或发灰，而不是更听话。
AdaLN 分支
DiT 里把「第几步 + 你要什么」压成一组缩放/平移参数，去调每个 block 的归一化层。H3 约 13B 参数在这里，它承载条件信息怎么影响主干。
反向 CFG
两种含义，都不是「符号写反」那种 bug：① 负向引导——把空提示换成「你不想出现的东西」，结果 = 负提示 + s × (正提示 − 负提示)，作用是把它推离模糊/水印/低质量；② 反推编辑——沿 CFG 路径把已有图/视频反推回噪声，再按新提示重画，保留构图只改内容。两者都要「能算两遍前向」，蒸馏过的 H3 直接调不出来。
adapter 头
夹在中间的小投影层：文本编码器输出 → DiT 维度的映射、新模态（音频/首帧/参考图）的入口投影、新任务的输出头。参数很少，但接上就必须单独训。

「SFT 要改 CFG 或 adapter 头」通常指下面三种情况，先分清是哪一种再动手。

1
条件变了加首帧、加音频、换文本编码器 → 输入维度对不上，必须新增 adapter 头，冻结主干只训这一小段。最常见也最正常。
2
数据是用 CFG>1 采的数据分布和模型原生分布不一致，SFT 会学到错误配对。蒸馏过的模型要么全程 1.0，要么把 guidance 当条件重训 embedding，基本不划算。
3
只是想调「听话程度」别动 CFG，去调提示词或奖励权重。
自查：SFT 后画面发灰 / 过曝 / 越训越糊 → 先查 guidance 有没有被改；条件完全不起作用或报维度不匹配 → 查 adapter 头有没有接上。

六项验收（缺一项都别加步数）

1 采样等价
σ=0 时 SDE 输出与原始 ODE 逐像素接近（允许极小误差）。
2 log-prob 可信
同一批样本重算两次，log-prob 差在 1e-4 量级以内。
3 奖励有方差
组内 16 条样本的奖励不能全相同，std 明显大于 0。
4 音视频都在
抽样 20 条，音频非静音、时长与视频一致。
5 画面不退化
代理分上升的同时，人工抽检的清晰度/结构不变差。
6 权重真生效
LoRA 合并后重新采样，输出确实变了，且不是变糊。
最贵的错误：跳过第 1、2 项直接开训。此时梯度可能来自一个错误的概率，训练曲线照样「好看」，但你拿到的模型是坏的，而且几百卡时已经烧掉了。

11少步蒸馏：DMD 家族与注意力加速

少步蒸馏训练能用更少次 DiT 前向完成生成的 student；注意力内核降低每次前向成本；二采改变前向发生的空间尺度。三者是不同开关，速度收益不能简单相乘。

11.1 H3 本地 DMD：一次 student 更新

本地 trainer 目标配置为 4-NFE LoRA。训练期有冻结 Teacher、Student 和可训练 Fake-score；推理期只保留 Student。Teacher score 与 fake score 的差估计 student 输出分布应移动的方向。

1
生成。Student 按配置的 4 个 NFE rollout 得到 latent G；随机抽 terminal step，梯度只经过最后一个 student step。
2
扰动。构造 x_t=(1−σ)G+σε，同一带噪样本分别送入冻结 Teacher 与 Fake-score。
3
求校正方向。按 H3 velocity 约定还原 x0=x_t+σv，计算 g≈(x0_fake−x0_teacher)/mean(|G−x0_teacher|)。
4
更新 Student。用 stop-gradient 伪目标 G−g 做平方损失，即 L=1/2·||G−stopgrad(G−g)||²。这是把分布梯度传回生成结果，不是拿 teacher 视频逐帧普通回归。
5
更新 Fake。Fake 拟合 student 生成样本的噪声/速度目标（代码对应 G−ε）。本地更新比为 student 1 次 : Fake 5 次。

源码与 DMD loss：H3 trainer、同目录 math.py；配置为 DMD YAML。该配置是 4 NFE、768×1344×243，使用 prompt_cache 而不读成对真实视频。H3 使用连续 data-fraction 时间及自己的 velocity 符号；迁移公式前先核对坐标约定。

11.3 SGMD：一次迭代的两个更新

  1. Student rollout：按随机终止点运行 4-NFE student，得到音视频 latent；加噪后让 Teacher 与 Fake-score 对同一状态预测。
  2. Student 更新：生成器目标是 teacher-stop-gradient Fisher loss + λ·NR（negative residual）。Fake 参数冻结，但 fake prediction 对输入保留梯度，校正信号可回到 student latent。
  3. Fake 更新：生成的 latent stop-gradient，用 λ·RC（residual contraction）更新 Fake-score。代码另算 velocity MSE 作为诊断项；优化器实际拿到的是 RC loss。
  4. 配置差异：本地每轮 student:Fake=1:1；phase2 画布 704×1280×209、λ=.05。它不同于 DMD 的 1:5 更新节奏。

11.4 4 NFE 不代表“完整生成只跑了四次网络”

NFE 指 student 部署时一次样本执行的 DiT 调用次数。训练还会调用 teacher、Fake 并做多次更新，训练开销高于部署；teacher/Fake 不随 student adapter 上线。LoRA 训练步数、采样 NFE、优化器更新次数是三种不同的“步数”。少步 adapter 需匹配 scheduler、noise schedule 与分辨率分布，随意改成 1-step 或换 scheduler 没有保真保证。

11.6 注意力加速：降低单步成本

类别例子改动与代价
精确高效内核FlashAttention分块计算降低显存读写，保持数学结果；收益受 GPU、序列长度和后端实现影响

更多训练目标见 h3.md、papers.md。注意力加速是每步算子层，二采是流程层；与少步 student 组合时，端到端收益需实测。

12二阶段采样与 SeedVR 恢复

二采是推理时的尺度切换：低分辨率先定构图、主体和运动，再放大 latent、重新加噪，在高分辨率继续去噪。它省一部分高清 token 计算，但增加 upscaler 和第二段采样成本。

T₂ ≈ N₁·c_low + T_up + N₂·c_high + T_decode

若宽、高各减半，空间 token 约为 1/4；全注意力二次项的单步注意力开销理论上约为 1/16。真实总耗时还含 DiT 其它算子、VAE、latent upscaler、显存和调度，须以同硬件端到端测量为准。所以 8+5 往往比同 13 步全程高清快，却通常慢于 4-step 高清直出。

12.2 latent 二采如何接轨迹

1
低清 draft。以较少 token 生成主体、布局和运动；画布需满足 VAE/patch 对齐。
2
latent 尺度放大。本地实现把 packed latent 还原为空间/时间结构，经学习式 3D latent upscaler 放大，再按 H3 的 24 通道 latent 与 patch 约定重新打包。
3
按目标噪声重加噪。xσ=(1−σ)x0+σε。高 σ 重画更多，利于生成新高频，但更容易偏离 draft；低 σ 较保守，新增纹理空间也小。
4
高清 refine。按 scheduler 剩余步数继续 H3 去噪。音频没有空间放大，但要与视频进度同步调度，避免时长和对齐断开。

12.3 SeedVR：为什么慢一点但可能更清晰

SeedVR 是视频恢复框架；SeedVR2 使用一步扩散与对抗式后训练、特征匹配和自适应窗口注意力恢复视频。一步是恢复模型自己的步数，仍要跑一个独立的大网络；不等于低成本 resize，也不减少 H3 采样步。输入缺少纹理时，恢复模型会推断并补细节，因此总时间上升但观感可能更锐；推断也意味着局部内容可能被改写或幻觉。仓库 SwiftVR 集成只能称 SeedVR2-family，不能认定加载的就是官方 SeedVR2 checkpoint。

本地参数并非统一默认：SGLang CLI 对非 480P 默认 8+5、480P 默认旁路；Agnes API mapping 的 split-step 默认 4，且可用环境变量覆盖。这是不同入口的默认配置。归档 e2e 日志在 qwen3_asr 配置注册时导入失败，源码/配置存在不代表生产服务已跑通。

实现细节见 h3.md 第 6 节、二阶段采样专题 和随归档检查的 SGLang CLI/API 参数映射。服务器专用集成包未纳入公开快照。

14采样参数手册

这一节回答一个具体问题：同一条提示词，为什么两次跑出来不一样。参数分成五组，每组只有一两个真正影响画质，其余是复现性问题。

第一组 · 随机性

seed 种子
决定初始噪声那个张量。确定性采样下，种子 + 提示词 + 步数 + 分辨率相同，结果应当完全一致。换卡、换 attention 后端可能有微小差异，因为浮点累加顺序不同。
latent 形状
由分辨率和帧数决定（H3：边长取 32 的倍数，帧数满足 17n+5）。改分辨率会改变种子的语义 —— 同一个种子在不同分辨率下不是「同一张图」。
噪声偏移
有的实现会做噪声均值偏移或 offset，影响整体亮度和对比。跨实现对比时容易踩坑。

第二组 · 噪声强度与时间表

sigma σ
就是「噪声有多强」。t=1 是纯噪声、t=0 是干净数据，σ 是同一个量的另一种写法。看到 σ 就翻译成「现在有多脏」。
SDE 里的 σ_t
每一步额外注入多少随机噪声。等于 0 就是确定性 ODE；越大探索越强，也越容易糊、越难复现。Flow-GRPO 训练时就是靠它才有采样多样性。
strength / start_timestep
二阶段 refine 用：从多脏的状态重新开始。0.2 只改细节，0.6 结构会变。这个值几乎决定二阶段画质提升有多大。
时间表 shift
流匹配常把采样点往高噪声侧偏（shift 设 2~3），让低噪声步更密。它直接决定「细节阶段分到几步」，是 4 步模型里最被低估的参数。
步数
4 步是加速方案的常态；降到 2~3 步开始崩结构，加到 8 步细节明显回升但成本翻倍。

第三组 · 引导

guidance / CFG
H3 已蒸馏，固定 1.0。按 SD 的习惯填 5 或 7 会过曝、色彩溢出、动作变僵。
negative prompt
只有真做两遍前向的 CFG 才生效。H3 单次前向，写了也基本没用。
APG / rescale
CFG 的替代方案，用来压制过曝。H3 上同样受限。
提示词权重
影响文本条件强度，过大时画面会「用力过猛」。

第四组 · 模型与权重

LoRA scale
不是 1.0 最好。0.6~0.9 往往更稳，turbo LoRA 与 DMD 叠加时尤其明显。调这个比重新训练便宜得多，先试它。
dtype
bf16 是默认。fp8 提速但细节掉，小目标（远处人脸）最先受害。
VAE 精度与分块
分块解码（tiled VAE）省显存，但接缝处容易糊；精度降到 fp16 以下也会损失纹理。
attention 后端
sdpa / flash / sage 数值不完全相同。sage 更快但做了近似，可能掉细节。换后端等于换结果，对比实验必须统一。

影响速查

参数调大调小H3 上的建议
seed换画面，无好坏—对比实验固定同一个
σ（SDE 噪声）更多样，更糊更稳，更容易复现训练时才需要，推理设 0
二阶段 strength结构会变，风险大细节补不上从 0.3~0.4 起调
shift细节步变多，结构步变少反之4 步时值得扫一遍
LoRA scale风格强，易过拟合效果弱0.6~0.9
dtype—fp8 掉细节评测用 bf16
复现失败最常见的三个原因：attention 后端不同、dtype 不同、LoRA scale 不同。这三个不统一，种子固定了也没用。
复现清单（八项）：seed、分辨率、帧数、步数、shift、dtype、attention 后端、LoRA scale（含 VAE 精度与后处理）。八项全写进实验记录，否则结果无法对比。

15推理引擎：ComfyUI 与 SGLang

这两个不是同一类东西。ComfyUI 是给人和工作流用的，SGLang 是给服务和吞吐用的。理解这一点，就能理解为什么很多权重只适配前者。

维度ComfyUISGLang
定位图形化工作流，创作与调试服务端高吞吐推理引擎
执行方式节点图，逐节点跑 PyTorch统一调度 + 定制 kernel + 图捕获
权重形态单文件 safetensors + 自定义键名映射HF 目录结构 + 引擎内注册的模型实现

不擅长高并发、上线服务新模型适配慢、权重需要转换

为什么很多权重只适配 ComfyUI

① 打包格式
ComfyUI 接受「一个 safetensors + 键名重映射表」，作者随手就能发；SGLang 要求标准 HF 目录、分片权重、config，还得在引擎里注册模型结构。
② 自定义算子
ComfyUI 节点里可以塞任意 Python：自定义 attention、自定义 VAE、自定义采样器。SGLang 不能执行任意代码，只认自己实现过的算子。
③ 量化格式
GGUF 和不少专有量化只有 ComfyUI 的对应节点能读。同一份「fp8 版本」在两个引擎里常常不通用。
④ 生态惯性
社区作者先做 ComfyUI 工作流，验证效果后才考虑引擎适配；适配的收益（吞吐）对个人作者没有意义。

H3 上的实际情况

引擎状态要注意什么

ComfyUIday-0 官方支持，模板默认用 pruned int8pruned 权重的 LoRA 兼容性受限，还会和部分 attention 节点冲突

vLLM-Omni官方 recipe面向吞吐，rollout 场景值得看

所以「有些权重只适配 ComfyUI」在 H3 上是具体可查的：Turbo LoRA 只认全量 bf16 或 int8_convrot，在 pruned 权重上会丢 adaln；pruned int8 又和部分 attention 节点冲突。这不是引擎有 bug，而是它们走的不是同一条数值路径 —— 同样解释了你为什么会看到「同一个种子的结果，换引擎就变了」。

对你们的意义：训练、评测、跑对比实验 → 原生 PyTorch 脚本或 diffusers，复现性优先；上线服务 → SGLang 已有官方支持，可以直接用；ComfyUI 适合调试与快速看效果，不适合当基线。RL 的 rollout 可以看 vLLM-Omni 那条路。

16.2 传统 CV：先分清「有没有 GT」

同一个 PSNR，在有参考和无参考两个场景里含义完全不同。生成模型评测通常没有 GT，所以真正能用的是无参考指标和分布指标，全参考指标只在「重建 / 超分 / 二采前后对比」里成立。

类别代表指标要 GT擅长坑
全参考 · 像素PSNR / SSIM要压缩、重建保真度高动态一错位就崩；和「好不好看」几乎无关
全参考 · 感知LPIPS / DISTS要纹理、模糊、局部结构失真逐帧算再平均，会把闪烁平均掉
无参考 · 画质DOVER · FAST-VQA · MUSIQ不要单条成片的技术 / 美学质量对「正确的运动模糊」不友好，高动态会冤枉
时序RAFT 光流 warp error、帧间残差不要运动流畅度、闪烁大位移时光流本身估错，误差会算到画面上
分布FID / FVD参考集多个模型横向比要求固定分辨率与帧数；单条视频算它没有意义
一句话记法：PSNR/SSIM 衡量「像不像原片」，LPIPS/DISTS 衡量「看起来像不像」，DOVER/FAST-VQA 衡量「这条片子本身有多清楚」，FVD 衡量「整批片子和真视频像不像」。四个问题不要混着问。

16.3 高动态场景：平均分会骗人

高动态（快速运动、大位移、旋转、镜头剧烈晃动、闪光）是最容易把评测做反的地方。原因不是指标不准，而是指标测的东西在动态段发生了变化：

  • 错位先于失真。位移一大，逐像素误差就被错位主导 —— 模型画得再好，PSNR 也低。要么先用光流把上一帧 warp 到当前帧再比，要么干脆别用全参考。
  • 正确的模糊被判成糊。高速运动本来就该有拖影，无参考画质模型会把它当成缺陷扣分。
  • 真实运动和闪烁混在一起。帧间差大，可能只是动得快。要先把运动补偿掉，剩下的残差才是闪烁。
  • 均值掩盖峰值。一条 5 秒片子里有 0.3 秒崩坏，全片平均几乎看不出来，但观众一眼就看到。
想确认什么别这么测换成这样
运动是否流畅逐帧 PSNR 取平均RAFT 光流 warp error（越低越顺），按运动幅度分桶报
有没有闪烁原始帧间 L1光流补偿后的残差 + 高频能量随时间的抖动
有没有糊 / 崩结构全片平均清晰度分取运动峰值帧看 Laplacian 方差、局部清晰度，看最低的 5% 分位
语义有没有丢只抽第一帧问 VLM首 / 中 / 尾 + 高动态段各抽几帧，原子问题逐条问，重复 3 次取多数
音画是否同步任何画质指标Omni 判口型与事件音对齐；再人工抽查 10 条
最实用的一条：按光流幅度把样本分成低 / 中 / 高三桶，分桶报分，不要只报总分。高动态桶里的掉分，往往就是模型真正的短板；混在总分里，会被大量静止镜头稀释掉。

16.4 VLM 与 Omni 当裁判：怎么问才稳

VLM 打分不是「丢进去问几分」这么简单，问法决定了方差。按稳定性从高到低有三档：

1
原子检查（最稳）。把要求拆成 yes/no 问题：「杯子里还有水吗」「人物左手是五根手指吗」「字幕有没有拼错」。答案可枚举，方差最小。
2
成对比较。同一 prompt 的两个结果，问「A 和 B 哪个更符合」。比绝对分稳，但要交换 A/B 顺序各问一次，抵消位置偏差。
3
绝对打分（最不稳）。1–5 分或 0–100 分。必须给 rubric（每一分对应什么），温度设 0，同一输入采样多次取中位数。
四个已知偏差：位置偏差（排在前面的更容易赢）、长度偏差（描述长的容易得高分）、自我偏好（同族模型互评偏高）、分辨率偏好（清晰度被当成质量）。做对比评测时，这四条至少要中和掉前两条。

Omni 的独有价值：它能同时接收画面和音轨，判断「关门声是不是和门关上同一时刻」「对白口型和语音是否对得上」「BGM 有没有压过台词」。这三件事没有任何纯视觉指标能测，而 H3 这类音视频模型恰恰最容易在这翻车。

16.7 和 RL 的关系：reward 不是评测

第 8 节讲过奖励怎么设计，这里补一句边界：reward 是训练信号，评测是验收。两者共用一套模型时，一定会出现 reward hacking —— 分数一路涨，人看越来越差。

  • 物理隔离：训练用的 reward 模型与验收用的判官不要是同一个 checkpoint，最好连家族都不同。
  • 数据隔离：VBench 的 prompt suite 是公开的，很容易被无意间混进训练集，指标会虚高。验收集自己留一份不公开的。
  • 分层看：训练中每 N 步跑一次固定 prompt 的小评测，把「语义分」和「画质分」分开画曲线 —— 只涨其一是典型的过拟合信号。
  • 别只看均值：记录最差 5% 的样本，RL 后期崩坏通常先从长尾开始。

17MiniMax H3 的提示词语法

H3 不接收「一段散文」，它接收的是一份带时间码的视听脚本。下面这套规则来自 context-ir 仓库的 h3-prompt-writing（base-en.txt / ref-en.txt），是模型侧的硬性格式，不是写作风格建议。

17.1 五种模式，三句固定首行

模式输入首行指令主体内容
T2VA纯文本无，直接从三个字段开始从零构建完整视听时间轴

FL2VA首帧 + 尾帧有（见下）描述首帧到尾帧的连续演变

17.3 镜头：编号、时间码、剪辑动词

  • [Shot 1] 不带时间码，直接接内容；后续镜头写作 [Shot 2] At 00:03.500, the camera cuts to ...。
  • 时间码必须严格递增，且不超过视频总时长。
  • 常规剪辑用 the camera cuts to / the shot cuts to / the shot transitions to / the shot changes to / the shot switches to；用户明确要求时才用 cross-dissolve / fade / wipe。
  • 剪辑要带来新信息（主体、空间、状态、视角或时间变了）。只是远近或轻微角度变化，用运镜，不要切镜头。
[Shot 1] Live-action, cinematic, a medium-wide shot frames a baker opening the shutters before sunrise. [Shot 2] At 00:05.000, the camera cuts to a close-up of steam rising from the sliced bread.

完整的运镜描述三个维度：类型决定怎么动，幅度决定变化范围，速度决定节奏。中等幅度、正常速度可以省略，但小幅度 / 大幅度、低速 / 高速要写出来。

类型写法
变焦Zoom In / Zoom Out（机身不动，只改焦距）

水平转动pan left / pan right（机位固定）
水平平移truck left / truck right（机位平移）

17.5 说话人、对白、画外音

说过话、唱过歌或发出画外人声的角色，一律给固定 ID：(S1)、(S2)；同时开口写 (S1,S2)。ID 跨镜头不变；从没出过声的角色不要给 ID。

角色首次出现时，要在 <d> 外面给出足以固定身份的信息：角色类型、年龄、性别、是否在画面内、音高、音色、语速、口音。

A young woman with a soft, breathy voice (S1) says: <d>[English] I get off at the next stop.</d> Two children (S1,S2) shout together: <d>[English] Wait for us!</d>
  • <d> 里只放语言标签 + 逐字原话。不翻译、不改写、不改标点。
  • 画外音固定用 says in an off-screen voiceover，并紧跟一句说明画面中角色嘴唇闭合：His lips remain completely closed.
  • 一句台词跨剪辑点时，在接缝处加 <scenetrans>，并说明音频在剪辑点延续；视频结束导致话没说完，用 <cutoff>。
  • 画面里真实可见的文字（招牌、字幕、霓虹灯）放进英文双引号，逐字保留，不翻译。

17.6 音景与配乐：叙事内 vs 叙事外

字段写什么长度不写什么
overall_soundscape环境音、物理动作音、非语言人声（风、雨、脚步、布料摩擦、呼吸、笑）1–4 句英文，一段连续文字不重复对白、歌唱和配乐

判断标准很简单：角色能不能听到。收音机、电视、手机铃声、街头艺人属于角色能听到的声音，写进 integrated_multimodal_description；只有观众能听到的配乐才进 non_diegetic_music。整段静音才写 N/A，没有音乐也写 N/A —— 不要留空。

17.7 Ref2VA：六段式 + 四类标签

带图 / 视频 / 音频参考时，不用基础模式，改用固定六段：

subject_definitions → 定义 <Subject N> / <Picture N> / <Video N> / <Audio N> summary → 一句话概括要生成什么 retention_analysis → 哪些属性必须保留（外观、服装、场景、声音） detailed_description → 带时间码的详细描述 overall_soundscape → 同基础模式 non_diegetic_music → 同基础模式
  • 四类标签各司其职：<Subject N> 是跨参考的同一主体，<Picture N> / <Video N> / <Audio N> 是按素材类型编号的引用源。
  • 六个段落全英文；仅 <d> 内的对白歌词与画面可见文字保留原语言。
  • 正文里出现的每个标签都必须先在 subject_definitions 里定义过，不能留未解析标签。

18病例排查：蒸馏加速后的视频模型

这一节记录一类具体的工程组合：基座视频模型 + 社区加速方案（turbo LoRA + DMD）+ few-step 采样。典型现象是远处人脸模糊、打斗动作僵硬。把结论写在这里，以后再遇到同类问题直接对照。

一句话根因

人脸模糊是空间高频丢了，动作僵硬是时间高频丢了。这两类信息要保留下来，需要两个前提同时成立：latent 分辨率够、采样步数够。加速方案恰好把这两个前提各压了一遍 —— 所以问题往往不是「模型不会画」，而是「路走得太短，细节没机会长出来」。

现象 → 主因排序

现象主因（概率最高）次因
远处人脸糊latent 里像素预算不够：远处人脸可能只占 1~2 个 token，压缩后就没了DMD 把高频平均化；LoRA 容量偏小；训练数据里远景人脸本来就少
打斗僵硬few-step 一步跳，运动轨迹被平滑成一条「平均路径」打斗在通用数据里是长尾；3D VAE 的时间压缩；DMD 倾向输出典型样本

A

B
把远处人脸裁出来放大放大后能看清 → 只是分辨率不够；放大后一团糊 → latent 里信息已经没了。

判据：放大后能看清 → 分辨率问题，改模型没用，走裁剪超分；放大后看不清 → 信息不可逆，别再调参。

控制变量与量化

不控住这些，实验就是白做：同一批 prompt、同一个种子（H3 确定性采样应可复现）；同分辨率、同帧数（边长 32 的倍数，帧数 17n+5）；guidance 一律 1.0；同一 VAE 解码、同一后处理，不要一边加超分一边不加；记录各组实际步数 —— 这是最容易漏的隐藏变量。

量化方式：按人脸框短边像素分桶（<24 / 24–48 / 48–96 / >96），每桶统计检测成功率、关键点置信度、面部 ROI 的 Laplacian 方差，再补一组打乱顺序的人工盲评（两人以上）。

预期：768p 的模型，远处人脸只有几十像素，原版大概率也是糊的。这不是 H3 独有的缺陷，而是行业共性。这个实验最大的价值，是让你们有数据支撑地决定「别再往这个方向投训练资源」。

问题类型该用什么为什么

RL 的陷阱：在人脸信息本来就丢光的模型上做 RL，最容易出现「奖励涨、观感更差」。先把蒸馏修好，再谈 RL。

稀疏注意力值不值得改

它解决的是速度和显存，不解决清晰度和运动。真正的风险是反噬：远处小目标的 token 本来就少，稀疏化最先砍掉的就是它们。

有意义
显存或速度是瓶颈，并且愿意用省下的预算去换更高分辨率、更长帧数 —— 那是间接改善。
没意义
指望它让脸更清楚、动作更自然。方向不对。
要做就做
只在低分辨率 / 高层阶段稀疏，精细阶段保持 dense；加显著性 token 保护，别把小目标裁掉。

注意力方案对照。名字不重要，看它落在哪一档：

方案复杂度画质代价实现难度
Dense（全注意力）O(N²)无，基线最低
固定稀疏（滑窗 / 带状 / 跨步）O(N·w)小，长程依赖变弱低，加 mask 即可
分块稀疏（按块选 top-k）O(N·k)中中，能用变长（varlen）接口
数据驱动稀疏（按分数选 token top-k）O(N·k)中到大，要微调高，得写定制 kernel
线性注意力（核方法替 softmax）O(N)大，基本要重训高
稀疏 + 线性混合O(N·k + N)中很高，两套路径都要调

回到被问到的三个名字：dense 就是第一行的基线；VDN 对应社区的 VDN-H3，属于线性混合注意力那一档（不是 token top-k 稀疏）；Sol attention 见下面这张卡 —— 它已经能对上号了，而且它不属于上面任何一档。

Sol-Attn 是什么（已确认）：它不是一种「更省算力的注意力形状」，而是 Sol-Engine / Sol-H3 这套引擎级加速方案里的注意力实现（arXiv 2609.35110，2026-09）。三件事拼起来：① 跨分辨率两阶段调度 —— 低分辨率快速定全局布局，高分辨率只补局部细节；② 两阶段之间用一个学习式的 latent-to-latent 映射衔接，不走「VAE 解码 → 放大 → 再编码」；③ 算子层自动搜索（论文叫 Recursive Self-Improvement，循环搜 kernel 融合与显存布局，同时校验数值一致性）。论文宣称端到端最高 30×、显存降 20%；ComfyUI 侧有社区插件，单卡实测大约 2~9×，取决于卡型与量化。
怎么看「87.26 s → 37.39 s（2.33×）」那张表：这是单段前向的对比，而且两边不止差在注意力 —— 一边是 dense + BF16，另一边是 Sol-Attn + MXFP8 量化 + CUDA graphs。2.33× 是三者叠加的结果，不能全记在注意力头上。要和自己方案比，先把 dtype、是否开 CUDA graphs 对齐，再看注意力本身贡献多少。
不难的
选哪些 token、算哪几个块 —— 几行 torch 就能写出来。
真正难的①
变长 attention 的高效 kernel。每个 head 选出的集合不同，Python 层先 gather 再喂进去，通常比 dense 还慢 3~10 倍，必须写 Triton/CUDA。
真正难的②
负载均衡。head 之间稀疏模式不同，SM 利用率不均；开序列并行还要多一轮通信。
真正难的③
训练不稳定。mask 每步都变，梯度噪声大，与 DMD / LoRA 叠加更不稳。
真正难的④
调参空间大。k 太省没加速、太小掉画质，且不同层、不同去噪步的最优 k 都不同，照抄论文容易翻车。
对当前组合的判断：4 步、33B、视频 —— 稀疏注意力不该当画质手段用。它唯一值得做的理由是用省下的算力换分辨率或帧数：能从 768p 上到 1080p，对远处人脸才是真收益（那是 token 预算问题）。真要做，选分块稀疏、只在低分辨率阶段开，别一上来就做数据驱动的 token top-k。

二阶段采样与远景人脸模糊的关系

全片二采能在高清 latent 上补整体纹理，但远处人脸仍可能只占很少 token，所以全局更锐不代表小脸恢复。Full-X0、Mid-trajectory、局部裁剪和 SeedVR 的原理、速度账与风险统一放在 第 12 节；这里保留排错重点：先判断问题来自低分辨率 token 预算，还是成片后的局部恢复。

排错顺序：先固定 base、LoRA、总 NFE 和 seed 与单阶段基线比较；结构/运动错，回到采样或蒸馏路线；只有小区域细节不足，再评估局部裁剪精修；已生成成片要增强时才比较 SeedVR 类恢复。

若是蒸馏损失：步数 4→8 试一遍；检查 DMD 的 fake score 更新频率；确认 turbo LoRA 与 DMD 的叠加顺序（两个都在改采样路径，很容易双重压缩）。
3
人脸：先上「检测 → 裁剪 → 超分 → 贴回」的两阶段流程，性价比远高于改模型。
4
动作：把「运动强度」做成条件标签（训练时按光流幅度分桶），推理时显式给高强度，比直接上 RL 更快见效。
5
稀疏注意力放最后，只当加速手段，不当质量手段。
社区加速方案的共性坑：固定 4 步、guidance 已蒸馏（别填 5/7）、LoRA rank 偏小、训练数据分布是别人的。继承的不只是权重，还有别人的数据短板 —— 所以「远处人脸」「打斗」这类长尾，天然是这类方案的弱项。

19远景人脸为什么糊：归因与修复

这是视频生成里被问得最多的问题，也是回答得最含糊的一个：「到底是 VAE 的锅还是 DiT 的锅？」准确答案是三个都有，但作用在不同环节 —— token 预算决定「有没有容量画」，VAE 决定「最多能画多细」，分块解码决定「拼回去时又损失多少」，后处理决定「最后还剩多少」。先定位丢在哪一段，再决定修还是重跑。

19.1 先把「糊」拆成四种

类型表现本质修法方向

压缩损失轮廓对、位置对，但睫毛、牙齿、瞳孔的细节一律没有；皮肤过度平滑VAE 的空间压缩把高频先丢掉了，解码时补不回来更高保真 VAE、tile VAE、修复模型

这四种在成片里经常混在一起，但处理的优先级完全不同。判断顺序应该是：先看结构对不对，再看是不是网格状，然后看细节有没有，最后才谈清晰度。结构都不对的时候做超分或人脸修复，只会把错误放大得更清楚。

19.2 一条链，五处丢信息

算一笔账就清楚了。H3 是 16× VAE + 2×2 patchify，也就是一个 latent token 覆盖 32×32 像素。704×1216 的成片里，一个远景人脸高 64 px，映射到 latent 就只有 2 格高 —— 整张脸 4 个 token。4 个 token 画不出眼睛、鼻子、嘴的相对位置，这不是糊，是信息容量根本不够。

反过来，近景人脸占 300 px 高，约 9×9 个 token，容量够了，此时的模糊才轮到 VAE 负责 —— 16× 压缩对皮肤纹理、睫毛、牙齿这类高频本来就不友好。

一句话结论：远景糊，主因是token 预算（DiT 侧的分辨率分配）；近景糊，主因是VAE 的高频截止。两者叠加时，先解决 token，再谈 VAE。

19.3 三步实验：怎么确定是哪一个

1
把 GT 视频过一遍 VAE 编解码。如果细节损失明显（尤其是皮肤、发丝、文字），VAE 就是天花板 —— 再怎么采样也超不过它。
2
裁出远景人脸放大看。放大后是平滑色块、没有任何结构，说明 token 不足；如果放大后有结构、只是纹理丢失，说明容量够、是 VAE 或后处理的问题。
3
同 prompt 用 2× 分辨率重跑。清晰度明显提升 → token 预算问题；依然糊 → VAE / 解码问题；结构变了但没变清楚 → 采样问题。

19.4 分块解码：第五处损失，而且是实现层的

前面几处都是模型结构决定的，还有一个经常被漏掉、却完全属于工程实现的来源：tiled VAE decode。高分辨率 latent 一次性解码激活会爆显存，几乎所有推理框架都会把 latent 切成块分别解码再拼回去 —— 空间上切 tile、时间上切 chunk，或者两者都切。

它带来的问题不是「均匀变糊」，而是有规律的、网格状的退化，所以很好认，但很容易被误判成 VAE 本身的压缩损失。

机制看到的现象为什么
每块独立解码块边界亮度 / 色调跳变、纹理断裂相邻块对同一区域的解释不一致，拼起来没有共享上下文
感受野被截断块边缘的发丝、人脸轮廓被抹平解码器在边界外补零，块的边缘只剩一半有效上下文
overlap 加权融合边界处一圈发虚，像蒙了层雾两块各自糊了一次，加权平均仍然是糊
时间维切段段边界那几帧闪一下、运动不连续3D VAE 的时间建模被切断，每段独立解码
伴随的精度差异局部颜色偏移、暗部色带分块常配合 fp16 累加，误差在边界累积
三步确诊：
  • 用同一个 latent，分别按 256 / 512 / 1024 的 tile 各解一次 —— 糊斑与接缝跟着 tile 尺寸移动，就是分块解码。
  • 量接缝位置 —— 是否等间距、间距是否约等于 tile 宽（或 tile 宽减 overlap）。
  • 裁一块出来单独解码 —— 块内部清楚、只有边界断层，说明信息没丢，是拼接丢的。
判断维度token 不足VAE 压缩分块解码
空间分布与「人脸占多少像素」强相关全图均匀，近景才明显网格状、周期性，与人脸无关
换分辨率明显改善基本不变不变（除非 tile 相对画面变大）
放大局部看平滑色块、无结构有结构、无纹理块内正常、边界断层
时间表现通常稳定稳定时间分块时逐段闪
解法加 token换 VAE / 补高频加大 tile 与 overlap、关 tiling

怎么治：

  • 加大 tile、提高 overlap。overlap 一般给到 tile 的 1/4 以上，越大越平滑、越慢；硬拼不加 overlap 是最差的做法。
  • 时间维尽量不切。temporal tile 设成全片，或至少重叠 4 个 latent 帧，否则段边界必闪。
  • 只切空间、不切时间。显存不够时优先沿高度方向切，比时空全切温和得多。
  • 交付级渲染关掉 tiling。分块只用于预览和批量出片；最终成片用整图解码，或用 batch 换显存而不是用 tile。
  • 编码侧同理。tiled encode 也会在边界引入漂移，i2i 精修、参考图编码、二采放大前的那次编码都会中招。
和第 14 节的分块解码参数是同一件事的两面：分块能省显存，但会增加拼接边界并可能延长解码时间；这里再补充画质代价 —— 它同时还拿画质换显存。而且这一层损失可以完全避免：它不来自模型，只来自你用的那套解码实现和参数。

19.5 三条修法，按「信息注入点」排

加 token（根本解）提高分辨率、二采到高分辨率、对人脸区域局部高分辨率重绘高（token²）人脸占比小、要求成片可交付

19.6 人脸修复算法谱系

「face refine」在不同团队嘴里指三类完全不同的东西，效果和风险差别很大：

类别代表原理风险
盲人脸修复GFPGAN · CodeFormer · RestoreFormer++学一个「退化人脸 → 清晰人脸」的映射，可用身份/质量先验约束对生成视频里「非真实」的脸容易过度平滑，表情变僵；逐帧跑会闪
扩散先验修复DiffBIR · SUPIR用扩散模型的生成先验 + 结构引导补细节，能「长」出新纹理会改内容，身份漂移；慢，且需要调 strength
局部重绘任意 inpaint / 视频重绘管线把人脸区域挖掉，用原 prompt + 参考帧重新生成最贵，但唯一能修「结构错」的办法
商业成片工具Topaz Video AI 类超分 + 人脸恢复 + 时序稳定打包黑盒，参数不透明，批量贵

工程上一条可用管线通常是：人脸检测（RetinaFace / SCRFD）→ 跟踪（ByteTrack 一类，拿到跨帧 ID）→ 5 点对齐仿射裁剪 → 修复模型 → 逆变换贴回 → 时序融合。检测和对齐这两步决定了后面所有步骤的上限 —— 框抖一下，脸就抖一下。

19.7 贴回时的四个坑

  • 抖动。逐帧独立修复，五官会轻微跳动。解法：按跟踪 ID 做时序平滑（EMA），或用光流把上一帧的修复结果 warp 过来当初值。
  • 接缝。裁剪框边界出现一圈突变。解法：羽化 mask + 泊松融合，必要时把裁剪框放大 20% 留过渡区。
  • 身份漂移。修完不像本人。解法：加身份相似度约束（ArcFace 特征余弦）、降低修复强度、用参考帧做引导。
  • 过度平滑。皮肤被磨平、牙齿变白、眼神光消失。解法：降 strength、混回原图的高频、只在结构区域重绘。
顺序反了会白干：先修脸再做全片超分，超分会把修复痕迹再糊一遍；正确顺序是先超分到交付分辨率，再做人脸精修，精修完不要再过 VAE 或任何重编码。

19.8 修还是重跑：一张决策表

情况建议理由
人脸高度 < 48 px重跑，提高分辨率或二采token 根本不够，修复只能贴一张「像脸的东西」

19.9 修完怎么证明修好了

  • 局部指标：裁出人脸区域单独算 LPIPS / DISTS；有参考身份时算 ArcFace 余弦相似度。
  • 时序指标：人脸区域的光流 warp error，确认修复没有引入新的抖动。
  • 不要只看均值：记录最差的那几张脸 —— 修复算法的失败通常是「大多数更好、少数崩掉」。
  • 盲测：修前 / 修后随机左右，10 条起，人工选「更自然」的那条；只问「更清晰」会系统性偏向过度锐化。
