# 原 F2 脚本：下载加速实验与运行说明

2026-11-10 实测结论：这组小视频适合 **5 文件并发、每文件单连接**。保留可选 Range 分段模块，但不默认开启。同期各 5 次对照，整批平均耗时由 3.458 秒降至 2.421 秒，减少 30.0%；总吞吐由 3.033 MB/s 升至 4.333 MB/s，提高 42.9%。

原目录 `./douyin-shared` 的脚本没有修改。仍使用先前的独立 `./server/.venv` 环境，没有安装新依赖，也没有修改 `shared system environment`。

## 1. 调研方法与本次取舍

| 方法 | 能解决的问题 | 本次结果 / 取舍 |
|---|---|---|
| 多文件并发 | 重叠不同作品的元数据、建连和下载等待 | 原脚本已有 4 并发；调整为 5，消除本组第五个任务的一轮排队，收益最稳定 |
| HTTP 连接池、Keep-Alive | 复用可用连接，减少重复建连 | 原脚本已使用共享 AsyncClient 和连接池，继续沿用 |
| 多连接 Range 分段，再按字节顺序拼接 | 让一个文件的多个区间同时传输，可能缩短单连接慢传的尾部 | 实测 2 段、最多 4 段及仅大文件分段；这组文件较小，额外探测/建连成本明显，未显示稳定优势 |
| 只重试失败片段 | 避免从头重复传输已完成内容 | 可选分段模块实现一次有界网络重试；范围、大小等协议错误立即拒绝 |
| 合理的块大小、临时文件、顺序写入 | 降低 Python 调度和碎片写入开销 | 原脚本已经使用 256 KiB 读取块；此次保持不变 |
| HTTP/2 多路复用 | 在服务端支持时复用一个 TCP 连接承载多个请求 | 未启用；需要额外可选依赖，且与多 TCP 连接分段不是一回事，不能保证必然更快 |
| 切换合适的 CDN 地址 | 可能改善单条链路和节点的时变表现 | 沿用原脚本已有地址及其失败回退，不更改鉴权/签名方案 |

分段下载的是 MP4 的**字节区间**。按原顺序拼接后应与原文件完全相同，不做视频转码，也不按视频时间切片。

IDM 还包括动态切分、慢段调度、连接复用等策略。本次实现是有界并发的固定 Range 分段，不将它等同于完整的 IDM 调度器。

参考原始资料：

- [IDM 官方功能说明：动态分段与连接复用](https://www.internetdownloadmanager.com/features2.html)
- [RFC 9110：Range、206 与 Content-Range](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests)
- [aria2 官方手册：split、min-split-size、max-connection-per-server](https://aria2.github.io/manual/en/html/aria2c.html)
- [HTTPX 官方文档：客户端连接池](https://www.python-httpx.org/advanced/clients/)
- [HTTPX 官方文档：HTTP/2 的能力与启用条件](https://www.python-httpx.org/http2/)

## 2. 瓶颈判断

上一轮最慢的 `7701675832264374922` 为 5,284,535 字节：从发起媒体请求到响应头约 3.064 秒，响应头到文件结束约 17.225 秒，共 20.289 秒。另一条 1.80 MB 文件的响应头等待约 2.488 秒，后续传输约 7.291 秒。因此旧轮次存在明显的媒体链路等待和慢传长尾，不只是元数据接口耗时。

同期不改代码重跑，原方案也曾从 12.843 秒变成 4.454 秒，后续更快。说明节点、缓存、连接与时间变化对结果影响很大。我们没有采集足够的底层网络指标来进一步区分具体原因，不能把历史到现在的全部提升归给算法。

链路变快后，这组实验的主要可优化项变成 **4 并发下第五个任务的排队**：同期原方案该视频从任务提交到结束平均 3.373 秒，5 并发时为 1.876 秒。其他作品未普遍加快，例如最大的那条平均耗时约从 2.181 秒变为 2.375 秒。收益来自整批等待重叠，不是每个连接都更快。

## 4. 实验顺序与结果

先固定文件并发为 4，比较分段数；再验证 5 文件并发与仅大文件分段，最后补充交错对照。每次写入独立的新目录，轮次之间等待 2 秒，此间隔不计入耗时。

| UTC 轮次目录 | 预先指定的执行顺序 | 用途 |
|---|---|---|
| 20261110T115305Z | 原方案、2 段、最多 4 段、原方案 | 初始探索 |
| 20261110T115440Z | 2 段、原方案、原方案、2 段、2 段、原方案 | 排查分段收益是否持续 |
| 20261110T115616Z | 原方案、5 并发、仅大文件分段、仅大文件分段、5 并发、原方案 | 调整并发和分段阈值 |
| 20261110T115833Z | 原方案、5 并发、5 并发、原方案、原方案、5 并发 | 默认参数确认 |

“最多 4 段”会保证每段至少约 256 KiB，小于约 1 MiB 的两条视频实际使用 2 段。“仅大文件分段”使用 5 文件并发，只对本组大于等于 4 MB 的文件启用 2 段。分段请求总并发上限为 12。

初始探索中，原方案为 12.843、4.454 秒，2 段为 3.586 秒，最多 4 段为 4.371 秒。但下一组中原方案为 2.527、2.426、4.047 秒，2 段为 3.585、3.052、3.620 秒。由此没有采用“固定分段一定更快”的结论。

默认参数确认合并最后两个轮次目录中的原方案和 5 并发结果，各 5 次，不混入先前的分段探索结果：

| 指标 | 原方案：4 文件并发 | 优化：5 文件并发 |
|---|---:|---:|
| 整批平均耗时 | 3.458 秒 | 2.421 秒 |
| 整批中位耗时 | 3.240 秒 | 2.492 秒 |
| 整批耗时范围 | 3.127–4.416 秒 | 2.088–2.671 秒 |
| 总字节数 / 累计批次时间 | 3.033 MB/s | 4.333 MB/s |
| 同上，换算为 Mbps | 24.267 | 34.666 |
| 5 次批次耗时 CV | 14.01% | 8.07% |
| 合并完整 100 ms 吞吐采样 CV | 187.21%（118 个采样） | 114.74%（68 个采样） |
| 无应用块到达的 100 ms 区间占比 | 69.49% | 42.65% |
| 单文件应用块到达间隔 P95 | 102.12 ms | 103.67 ms |

5 组相邻对照中，5 并发每次整批耗时都更短。平均耗时减少 30.0%，总吞吐提高 42.9%。批次波动和整批短时间吞吐波动有所改善；**单文件块间隔没有改善**，不能说修复了网络本身的抖动。

历史上一轮为 21.281 秒、0.493 MB/s，现在默认方案均值为 2.421 秒、4.333 MB/s，观察到约 8.79 倍吞吐差异。该历史对比受时间、CDN、缓存影响；更能反映此次调整收益的是上面的同期约 1.43 倍。

### 统计口径

- 整批计时从提交 5 个任务开始，到全部任务及大小/MD5 检查完成；包含元数据、排队、重定向、传输，以及分段时的探测和合并。排除首次发现这 5 个作品的博主分页阶段，因此与历史 `download_phase_seconds` 对应。
- 读取块保持 256 KiB。100 ms 统计为每轮首个媒体请求到最后媒体块结束间的完整区间，剔除最后不足 100 ms 的部分，再合并各轮样本。
- CV = 总体标准差 / 均值 × 100%。吞吐均值与整批总速度不同，因为前者只覆盖媒体区间、且剔除了尾部不足采样间隔的部分。
- 应用层“没有块到达”不等于链路完全没有数据，可能仍在等待填满应用读取块；这些指标不是网络 RTT 抖动或丢包率。
- 优化后许多轮次只有一个完整的 1 秒区间，因此报告中的 1 秒 CV 可能为 0，**不作为稳定性改善证据**。
- 样本只有 5 条小视频；没有验证大文件、不同博主、数十万条任务的长期吞吐上限。不能直接用本组结果推算长期日下载量。

## 5. 直接运行已验证入口

服务器项目与环境对应关系：

```text
原目录（未修改）：./douyin-shared
复制与测试目录：  ./original-f2-test
独立 Python 环境：./server/.venv
```

Cookie 仍使用测试目录已有的 `cookie.txt`，不需要在命令行或文档里写 Cookie。入口复用 `bounded_probe.py` 中先前已验证的运行时 F2 兼容适配；不改原脚本或 site-packages。此适配针对当前接口行为，不保证平台变化后长期有效。

```bash
root=./original-f2-test
cd "$root"
umask 077
export HOME="$root/.cache/home"
export TMPDIR="$root/.cache/tmp"
export XDG_CACHE_HOME="$root/.cache"
export UV_CACHE_DIR="$root/.cache/uv"
export UV_PROJECT_ENVIRONMENT=./server/.venv
export PYTHONDONTWRITEBYTECODE=1
export CUDA_VISIBLE_DEVICES=''

# URL 文本文件每行一条。使用新输出目录，避免原脚本跳过旧文件。
./server/.venv/bin/python run_f2_optimized.py \
  -i "$root/optimization/smoke.urls.txt" \
  -o "$root/output/my_new_run" \
  -c 5
```

默认 `--segments 1`，不额外探测 Range。`-c` 可配置，入口限制在 1–16；本次只确认 4 与 5，并未证明越大越好。

需要单独评估分段时，用新的输出目录显式添加：

```bash
./server/.venv/bin/python run_f2_optimized.py \
  -i "$root/optimization/smoke.urls.txt" \
  -o "$root/output/optional_range_test" \
  -c 4 --segments 2 --range-connections 12 --min-segment-kib 256 --max-file-mb 100
```

`--max-file-mb` 和 `--min-segment-kib` 仅在启用分段时生效。普通入口保持原下载函数行为，不额外限制文件大小。图片等非 MP4 内容仍交给原下载函数。

默认入口额外实际下载了同样 5 条视频，并独立核对大小和 MD5，通过结果见 `launcher_validation.json`。普通入口并未变成全面的内容验收系统；实验中的逐文件历史 MD5 对照由测速脚本负责。

## 6. 分段实现与边界

`range_downloader.py` 不依赖 F2 或浏览器，可由其他异步采集插件调用。分段数、最小片段大小、全局请求信号量、重试次数、最大文件大小，以及已知的大小/MD5 都是参数。

它先以 `Range: bytes=0-0` 检测支持；要求精确的 `206`、`Content-Range`、内容长度，且使用 `Accept-Encoding: identity`。每段按不同临时文件写入，全部完成后按原顺序合并，验证总长度；提供 `expected_md5` 时还验证整文件 MD5，再原子发布。服务端忽略 Range 返回 `200` 时，退回经过大小校验的单 GET；错误的 `206` 不拼接。只在临时子目录里清理本次片段。

若服务端提供强 ETag 或 Last-Modified，会用 If-Range 防止下载期间版本变更。取消或一段失败时，会取消并等待其他片段任务，不留后台请求。跨进程断点恢复、动态慢段再切分、跨 CDN 拼片都未实现。

7 项协议测试覆盖正常范围、忽略范围、范围错误、截断、内容损坏、MD5 不符和任务取消，已在本地及服务器独立 F2 环境通过。

本轮保持历史原客户端 `verify=False` 设置，以免同时改变 TLS 校验影响对照；这不是加速手段。

## 7. 报告与复现

本地新增代码保存在 `.cache/f2-original-test/`，服务器对应文件位于上述 `original-f2-test/` 根目录：`run_f2_optimized.py` 为可运行入口，`range_downloader.py` 为独立分段模块，`optimize_benchmark.py` 为测速脚本，`test_range_downloader.py` 为协议测试。它们复用既有的原脚本副本与 `bounded_probe.py`；没有替换其他采集入口。

本地 `runs/f2-optimization/` 包含：

- `summary.json`：指标、口径及来源轮次。
- `all_rounds.csv`：全部 22 轮结果。
- `same_five.csv`：逐视频大小、MD5、历史媒体耗时及同期总耗时。
- `comparison.png`：同期耗时和波动图。
- `validation.json`：110 次实验下载校验、最终 5 条 ffprobe/抽帧检查、源文件和共享环境核对、任务 PID 退出核对。
- `launcher_validation.json`：最终默认入口另行下载的 5 条校验。
- 各 UTC 目录：分轮 JSON、100 ms / 1 s CSV 与块到达记录。不含 Cookie 或媒体签名 URL。

服务器原始实验产物位于测试目录下 `optimization/<UTC 时间>/`，视频在各轮 `videos/`；本地只拉取报告，没有再拉取全部实验视频。
