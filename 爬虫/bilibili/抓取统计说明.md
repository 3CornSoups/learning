# B站抓取条数和耗时统计

服务器目录：`./bilibili`

统计已接入普通随机下载入口，也提供独立测试入口。**默认跳过超过300秒（5分钟）或时长未知的视频**；300秒允许，300.001秒会被跳过。

## 1. 平常下载时就会统计

```bash
cd ./bilibili
./run_search_random.sh "自然风景" --count 20
```

该命令会实际搜索和下载，同时统计，不是只检查信息。默认最多读取100条候选，最多选择20条满足条件的视频。

如果B站搜索要求验证，任务会停止，并保存 `blocked` 状态报告：搜索耗时仍有记录，下载阶段为0，因为没有执行下载。这不代表已成功搜索或下载。

## 2. 专门做一次性能测试

```bash
./run_benchmark.sh "自然风景" --count 20 --pool-size 100 --max-duration 300
```

独立入口为 `benchmark_crawler.py`，统计实现为 `crawl_statistics.py`。与普通随机下载入口使用相同的下载逻辑和统计口径。

需要登录状态时，文件里必须已保存有效Cookie。若服务器的 `bilibili.txt` 保存的是F12复制的单行Cookie值，可执行：

```bash
./run_benchmark.sh "自然风景" --count 20 --max-duration 300 --cookie-header-file ./bilibili.txt
```

Netscape格式文件改用 `--cookies 文件名`，两种参数不要混用。统计报告不会记录Cookie值。

无Cookie但有候选链接TXT时：

```bash
./run_benchmark.sh "自然风景" --candidates-file "候选链接.txt" --count 20 --max-duration 300
```

此时“搜索/读取”计时测的是读取TXT的耗时，不是B站实时搜索耗时。

只获取候选，不下载视频：

```bash
./run_benchmark.sh "自然风景" --search-only
```

只解析信息和筛选，不下载视频：

```bash
./run_benchmark.sh "自然风景" --candidates-file "候选链接.txt" --resolve-only
```

## 3. 终端和报告包含哪些统计

数量会分别记录：

- 搜索接口返回的记录数，或候选文件中的全部链接记录数。
- 进入候选池的条数：受 `--pool-size` 限制。
- 去重数、无效链接数、已下载跳过数。
- 实际检查候选数、真正发起视频信息解析的条数、解析成功和失败数。
- 搜索数据已知超过300秒的跳过数、解析后超过300秒的跳过数、时长未知跳过数。
- 最终选择数、调用下载器数、新下载完成数、下载失败数，以及下载阶段复用已有文件/历史记录的数量。

时间会分别记录：

- 搜索或读取清单耗时。
- 筛选与解析总耗时，及其中解析请求的耗时。
- 下载阶段总耗时：包含等待、重试和FFmpeg合并。
- 合并耗时、整个任务耗时。
- 每条视频的解析、下载、合并耗时，成功视频的平均下载耗时和最后一次下载调用耗时。

“读取多少条”“解析多少条”“成功下载多少条”是不同口径。达到目标数量后会停止继续解析，所以实际检查数可能小于读取数。已经下载的文件不会被计入本次新下载成功。

带“其中”的时间是阶段内分项，不能再与对应阶段总耗时相加。完成文件大小是磁盘文件体积，不是精确网络流量。

## 4. 报告在哪里

每次运行保存独立目录：

```text
reports/年月日_时分秒_微秒/report.json
reports/年月日_时分秒_微秒/report.md
```

最近一次报告：

```bash
cat reports/latest.md
```

机器可读数据：`reports/latest.json`。时间精度保存在JSON里，终端通常显示3位小数。

即使任务被验证拦截、下载失败或按Ctrl+C中断，已经获得的统计仍会保存。报告里的 `status` 会说明结果，不会把失败记成成功。

## 5. 本次服务器实测

为避免大量下载，只做了小规模验证：读取2条已知候选，检查并解析2条；其中1条超过5分钟被跳过，另1条80.384秒的视频下载完成，文件约8.71MiB。

- 读取候选：2条。
- 超过5分钟跳过：1条。
- 新下载成功：1条。
- 下载阶段耗时：约6.088秒。
- 筛选解析耗时：约6.928秒。
- 整体耗时：约13.022秒。

本次使用候选文件，因此不是实时搜索速度测试。这个视频本身是含音频的单文件流，不需要合并，合并耗时为0。分离音视频流需要合并时，会另行记录合并耗时。

完整实测报告在：

```text
reports/20261110_194540_970486/report.md
```

另外通过了300秒边界、去重、历史跳过、已有文件复用、下载失败分类、合并计时、以及搜索被拦截仍保存报告的模拟测试。
